## 16. Kubernetes 核心架构

### 16.1 设计理念

Kubernetes 的核心可以概括为三句话:

1. **声明式 API**:你提交的是"期望状态"(YAML),不是"执行命令";系统持续向期望状态收敛。
2. **控制器循环(Reconciliation Loop)**:每个控制器不断对比"期望状态"与"实际状态",并采取动作消除差异。
3. **一切皆资源**:Pod、Service、ConfigMap、PVC、CRD 都是 API 资源,统一通过 kube-apiserver 读写 etcd。

### 16.2 整体架构图

```text
                          ┌──────────────────────────────────────────────┐
                          │            Control Plane(k8s01)              │
                          │                                              │
  kubectl / Dashboard ───▶│  kube-apiserver ◀──────────────▶ etcd        │
  kubeadm / CI/CD         │        ▲                                     │
                          │        │ watch / informer                    │
                          │  ┌─────┴──────────────────┐                  │
                          │  │ kube-scheduler         │                  │
                          │  │ kube-controller-manager│                  │
                          │  └────────────────────────┘                  │
                          └───────────────┬──────────────────────────────┘
                                          │ kubelet 上报 / apiserver 下发
                 ┌────────────────────────┼────────────────────────┐
                 ▼                        ▼                        ▼
      ┌────────────────────┐   ┌────────────────────┐   ┌────────────────────┐
      │ k8s02(worker)      │   │ k8s03(worker)      │   │ 更多节点…          │
      │  kubelet           │   │  kubelet           │   │                    │
      │  kube-proxy        │   │  kube-proxy        │   │                    │
      │  containerd        │   │  containerd        │   │                    │
      │  Pod / CNI / Pods  │   │  Pod / CNI / Pods  │   │                    │
      └────────────────────┘   └────────────────────┘   └────────────────────┘
```

### 16.3 控制平面组件

| 组件 | 作用 | 说明 |
|---|---|---|
| **kube-apiserver** | 集群唯一入口 | 提供 REST API,负责认证(Authentication)、授权(RBAC)、准入控制(Admission);所有组件都通过它读写集群状态 |
| **etcd** | 键值存储 | 保存整个集群的状态(唯一事实来源);必须定期备份,丢失 etcd ≈ 丢失集群 |
| **kube-scheduler** | 调度器 | 监听"未绑定节点"的 Pod,先过滤(资源、亲和性、污点),再打分,选出最合适的节点;它只做决策,不负责启动容器 |
| **kube-controller-manager** | 控制器集合 | 包含 Deployment、ReplicaSet、Node、Endpoint、ServiceAccount 等几十个控制器,持续把实际状态推向期望状态 |
| **cloud-controller-manager** | 云厂商集成 | 对接云负载均衡、云盘、节点生命周期等;自建集群通常不部署 |

### 16.4 工作节点组件

| 组件 | 作用 |
|---|---|
| **kubelet** | 节点代理。监听分配给本节点的 Pod,通过 CRI 调容器运行时创建/销毁容器,上报节点与 Pod 状态,执行探针 |
| **kube-proxy** | 实现 Service 的访问规则(ClusterIP/NodePort),通过 iptables、IPVS 或 nftables 做转发与负载均衡 |
| **容器运行时** | 实际运行容器的组件:本集群为 **containerd 2.4.2**(K8s 1.24 起移除 dockershim,Docker 不再是运行时首选) |
| **CNI 插件** | 给 Pod 分配 IP、打通跨节点网络:本集群为 **Flannel(vxlan)** |

### 16.5 常用插件(Addons)

| 插件 | 作用 | 本集群状态 |
|---|---|---|
| CoreDNS | 集群内 DNS,Service 名解析 | ✅ 已部署(kube-system) |
| Flannel | CNI 网络插件 | ✅ 已部署(kube-flannel) |
| Kubernetes Dashboard | Web 控制台 | ✅ 已部署(NodePort 32005) |
| metrics-server | 提供 CPU/内存指标,支持 `kubectl top`、HPA | ❌ 未安装 |
| Ingress Controller | 七层入口(域名/路径路由) | ❌ 未安装 |
| Prometheus / Grafana | 监控与可视化 | ❌ 未安装 |

### 16.6 一次 Pod 创建的完整流程

1. 用户执行 `kubectl apply -f pod.yaml`,请求发往 kube-apiserver
2. apiserver 完成认证、授权、准入校验后,把 Pod 对象写入 etcd
3. kube-scheduler 监听到"未调度"的 Pod,完成节点选择,把绑定结果写回 apiserver
4. 目标节点的 kubelet 监听到分配给自己 Pod,调用 CRI(containerd)拉取镜像、创建容器
5. CNI 插件为 Pod 分配 IP,配置网络
6. kubelet 把 Pod 状态上报给 apiserver(状态写回 etcd)
7. Endpoint 控制器更新 Service 的 Endpoints/EndpointSlice
8. kube-proxy 监听 Endpoints 变化,更新节点上的转发规则

### 16.7 网络模型(三种 IP)

| 类型 | 含义 | 示例 |
|---|---|---|
| Node IP | 物理机/虚拟机网卡地址 | 192.168.150.170 |
| Pod IP | 每个 Pod 独立 IP,跨节点可直接路由(由 CNI 实现) | 10.244.1.10 |
| ClusterIP | Service 的虚拟 IP,由 kube-proxy 转发到后端 Pod | 10.96.x.x |

- 同一个 Pod 内的多个容器共享网络命名空间,通过 `localhost` 互访。
- 跨节点 Pod 通信由 Flannel 的 VXLAN 隧道封装。
- 集群 DNS(CoreDNS)把 `ai-oj-auth` 这样的 Service 名解析成 ClusterIP。

## 17. 核心资源对象详解

### 17.1 Pod:最小调度单元

- Pod 是一个或多个容器的集合,共享网络和存储卷。
- 生命周期状态:`Pending`(等待调度/拉镜像)→ `Running` → `Succeeded` / `Failed`;异常时 `CrashLoopBackOff`、`ImagePullBackOff`。
- 常见容器类型:
  - **主容器**:业务进程
  - **initContainer**:按顺序执行,全部成功后才启动主容器(常用于初始化、等待依赖)
  - **sidecar**:与主容器并行,如日志采集、代理
- **探针**:
  - `livenessProbe`:失败会重启容器
  - `readinessProbe`:失败会把 Pod 从 Service 摘除(不重启)
  - `startupProbe`:给慢启动应用更长的初始化时间

### 17.2 工作负载控制器

| 控制器 | 特点 | 典型场景 |
|---|---|---|
| **Deployment** | 管理 ReplicaSet,支持滚动更新/回滚/扩缩容 | 无状态 Web 服务 |
| **ReplicaSet** | 保证副本数,一般不直接使用 | 由 Deployment 自动管理 |
| **StatefulSet** | 稳定网络标识、有序部署/扩缩、可绑定独立 PVC | 数据库、消息队列等有状态服务 |
| **DaemonSet** | 每个节点运行一个 Pod | 日志采集、网络插件、监控 Agent |
| **Job** | 运行到成功结束 | 一次性迁移、批处理 |
| **CronJob** | 按 Cron 表达式定时创建 Job | 定时备份、清理任务 |

Deployment 的层级关系:`Deployment → ReplicaSet → Pod`。更新镜像时会创建新的 ReplicaSet,逐步替换旧 Pod。

### 17.3 Service 与 Ingress

| 类型 | 说明 | 访问方式 |
|---|---|---|
| **ClusterIP** | 默认类型,仅集群内可访问 | `http://<service-name>:<port>` |
| **NodePort** | 在每个节点暴露一个高位端口(30000~32767) | `http://<节点IP>:<nodePort>` |
| **LoadBalancer** | 对接云厂商负载均衡(自建集群需 MetalLB 等) | 外部 LB 地址 |
| **ExternalName** | 把 Service 映射到外部域名(CNAME) | 集群内 DNS 解析 |

- Service 通过 **selector** 选择 Pod,自动维护 **Endpoints/EndpointSlice**(后端 Pod IP 列表)。
- **Headless Service**(`clusterIP: None`)直接返回 Pod IP,常用于 StatefulSet。
- **Ingress** 是七层入口(域名/路径/TLS),需要一个 Ingress Controller(如 ingress-nginx)才能真正生效。

### 17.4 配置与存储

**ConfigMap / Secret**

| 对象 | 用途 | 注意 |
|---|---|---|
| ConfigMap | 非敏感配置(环境变量、配置文件) | 修改后需重启 Pod 或依赖热加载 |
| Secret | 敏感数据(密码、Token、证书) | 默认只做 base64 编码,不等于加密;需配合 RBAC 与加密存储 |

**存储卷**

| 类型 | 生命周期 | 场景 |
|---|---|---|
| emptyDir | 随 Pod 删除 | 临时缓存、sidecar 共享 |
| hostPath | 随节点,Pod 换节点会丢 | 实验环境、节点级数据 |
| PV / PVC | 独立于 Pod | 生产持久化,由 StorageClass 动态供给 |
| StorageClass | 定义存储类型与供给方式 | 动态创建 PV |

PV 访问模式:`ReadWriteOnce`(单节点读写)、`ReadOnlyMany`、`ReadWriteMany`、`ReadWriteOncePod`。回收策略:`Retain`(保留)、`Delete`(删除)、`Recycle`(已废弃)。

### 17.5 调度机制

| 机制 | 作用 |
|---|---|
| `nodeSelector` | 最简单的节点选择,按标签匹配 |
| `nodeAffinity` | 更灵活的节点亲和性(required/preferred) |
| `podAffinity` / `podAntiAffinity` | 让 Pod 靠近或远离其他 Pod(如同一服务副本打散) |
| **Taint(污点)** | 节点拒绝某些 Pod,如 master 的 `node-role.kubernetes.io/control-plane:NoSchedule` |
| **Toleration(容忍)** | Pod 声明可以容忍某个污点 |
| 资源 requests | 调度器按 requests 判断节点是否有足够资源 |

**QoS 等级**(由 requests/limits 决定):

- `Guaranteed`:requests = limits(最高优先级)
- `Burstable`:设置了 requests 但小于 limits
- `BestEffort`:都没设置(最容易被驱逐)

### 17.6 命名空间与 RBAC

- **Namespace**:资源隔离边界,`kubectl get pods -n ai-oj`;部分资源(如 Node、PV、ClusterRole)不属于命名空间。
- **RBAC** 四件套:
  - `Role` / `ClusterRole`:定义"能做什么"(动词 + 资源)
  - `RoleBinding` / `ClusterRoleBinding`:把角色绑定到用户/组/ServiceAccount
- **ServiceAccount**:Pod 内进程访问 apiserver 的身份,Token 自动挂载到 `/var/run/secrets/kubernetes.io/serviceaccount`。

### 17.7 资源管理与弹性

- `requests`:调度依据,保证最小资源
- `limits`:运行时上限;CPU 超限被节流,内存超限会被 OOMKilled
- **HPA**:基于 CPU/内存/自定义指标自动扩缩副本,需要 metrics-server
- **PDB**:保证驱逐/升级时最少可用副本数

### 17.8 常用 YAML 模板

Deployment + Service:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: default
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27-alpine
          ports:
            - containerPort: 80
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { cpu: 500m, memory: 256Mi }
          readinessProbe:
            httpGet: { path: /, port: 80 }
            initialDelaySeconds: 5
---
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: default
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30081
```

ConfigMap:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_MODE: "production"
  application.yaml: |
    server:
      port: 8080
```

PV / PVC(本地盘示例):

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: local-pv
spec:
  capacity:
    storage: 5Gi
  accessModes: ["ReadWriteOnce"]
  persistentVolumeReclaimPolicy: Retain
  hostPath:
    path: /data/local-pv
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 5Gi
```

## 19. 常见故障排查速查表

| 现象 | 常见原因 | 排查命令 |
|---|---|---|
| Pod `Pending` | 资源不足、nodeSelector 不匹配、污点未容忍、PVC 未绑定 | `kubectl describe pod` 看 Events;`kubectl get nodes` 看资源/污点 |
| `ImagePullBackOff` / `ErrImagePull` | 镜像名/标签错误、私有仓库未认证、网络不通 | `kubectl describe pod`;`crictl images`;`ctr images ls` |
| `CrashLoopBackOff` | 应用启动报错、配置错误、依赖不可达、端口冲突 | `kubectl logs <pod> --previous`;检查 ConfigMap/Secret/依赖服务 |
| `OOMKilled` | 内存 limit 太小、JVM 堆超过 limit、内存泄漏 | `kubectl describe pod` 看 Last State;调大 limit 或 `-Xmx` |
| `Evicted` | 节点磁盘/内存压力 | `kubectl describe node`;清理镜像/日志;kubelet 驱逐阈值 |
| Pod 一直 `Terminating` | Finalizer 阻塞、节点失联 | `kubectl get pod -o yaml` 看 finalizers;必要时强制删除 |
| 节点 `NotReady` | kubelet 停止、网络插件异常、磁盘满 | `systemctl status kubelet`;`journalctl -u kubelet`;`df -h` |
| Service 访问不通 | selector 不匹配、targetPort 错误、Endpoints 为空 | `kubectl get endpoints`;`kubectl describe svc` |
| DNS 解析失败 | CoreDNS 异常、NetworkPolicy 拦截 | `kubectl -n kube-system get pods -l k8s-app=kube-dns`;Pod 内 `nslookup kubernetes` |
| PVC `Pending` | 没有可用 PV / StorageClass | `kubectl describe pvc`;`kubectl get pv,sc` |
| `kubectl top` 无数据 | metrics-server 未安装/未就绪 | `kubectl -n kube-system get deploy metrics-server` |
| 证书过期 | kubeadm 证书默认 1 年 | `kubeadm certs check-expiration`;`kubeadm certs renew all` |
| kubelet 反复重启 | swap 未关闭、cgroup 配置错误、容器运行时异常 | `journalctl -u kubelet -n 100`;`systemctl status containerd` |

## 20. 学习路径与练习建议

### 20.1 推荐学习顺序

| 阶段 | 内容 | 目标 |
|---|---|---|
| 第 1 阶段 | Pod / Deployment / Service / ConfigMap,`kubectl` 基本操作 | 能部署一个可访问的 Web 应用 |
| 第 2 阶段 | 滚动更新/回滚、探针、资源 requests/limits、命名空间 | 理解发布与稳定性 |
| 第 3 阶段 | PV/PVC、StatefulSet、Ingress、NetworkPolicy | 能部署有状态服务与七层入口 |
| 第 4 阶段 | 调度(亲和性/污点)、HPA、RBAC、监控、GitOps | 接近生产实践 |

### 20.2 在本集群上的练习清单

```bash
# 1. 第一个 Pod
kubectl run hello --image=nginx:1.27-alpine --port=80
kubectl get pods -o wide
kubectl port-forward pod/hello 8081:80
# 浏览器访问 http://127.0.0.1:8081

# 2. Deployment + 滚动更新 + 回滚
kubectl create deployment web --image=nginx:1.27-alpine --replicas=3
kubectl set image deploy/web nginx=nginx:1.28-alpine   # 注意容器名
kubectl rollout status deploy/web
kubectl rollout undo deploy/web

# 3. Service 暴露
kubectl expose deploy/web --port=80 --type=NodePort
kubectl get svc web

# 4. ConfigMap / Secret 注入
kubectl create configmap demo-cm --from-literal=APP_MODE=dev
kubectl create secret generic demo-secret --from-literal=password=123456
```
